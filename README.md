# openJiuwen

Харнесс на базе openJiuwen: оценивает расход на каждую задачу из папки задач, выбирает набор, который укладывается в бюджет токенов и лимит времени, и решает его агентом, тратя как можно меньше вызовов модели.

## Требования

- Python 3.12 (версия зафиксирована в `.python-version`: 3.12.10)
- Доступ к OpenAI-совместимому API с моделями из `config.py`

## Установка

Windows (PowerShell):

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Linux / macOS:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Настройка `.env`

Скопируйте шаблон и заполните значения:

```bash
cp .env.example .env
```

| Переменная     | Обязательна | Описание                                                        |
|----------------|-------------|-----------------------------------------------------------------|
| `LLM_BASE_URL` | да          | Адрес OpenAI-совместимого API, например `https://host/v1`       |
| `LLM_API_KEY`  | да          | Ключ доступа к API                                              |
| `BUDGET`       | нет         | Бюджет токенов на весь прогон (целое число). Без него берётся `DEFAULT_BUDGET` из `config.py` |
| `TASKS`        | нет         | Путь к папке с задачами, по умолчанию `./task-dir`              |
| `MODELS`       | нет         | Модели через запятую, если ключ даёт не все (по умолчанию все из `config.py`) |
| `USE_JUDGE`    | нет         | `1` — включить оценку моделью-судьёй (по умолчанию выключена, оценка берётся из таблицы) |
| `JUDGE_MODEL`  | нет         | Модель-судья вместо `JUDGE_MODEL_NAME` из `config.py`, если у провайдера другие имена моделей (например, OpenRouter) |
| `JUDGE_NO_REASONING` | нет    | `1` — просить провайдера (OpenRouter) выключить рассуждения судьи, как у моделей `-noreason` |
| `TRAJECTORIES` | нет         | Файл JSON Lines, куда по каждой задаче дописываются оценка и фактический расход (данные для калибровки оценок) |
| `OUT`          | нет         | Файл (или папка) для `solutions.json`. По умолчанию рядом с кодом, а если там нельзя писать — в папке задач |
| `LOG_DIR`      | нет         | Папка для `main.log`. По умолчанию рядом с кодом, а если там нельзя писать — во временной папке |
| `NOREASON_VIA_REQUEST` | нет  | `1` — модель с суффиксом `-noreason` отправляется как базовая с выключенными рассуждениями. Нужно на OpenRouter, где отдельных моделей без рассуждений нет; на прокси соревнования не задаётся |
| `PARALLEL_SESSIONS` | нет    | Сколько задач решать одновременно, по умолчанию 5. На бесплатном тарифе потолок 3 запроса сразу |

Пример `.env`:

```dotenv
LLM_BASE_URL=https://your-llm-endpoint/v1
LLM_API_KEY=your-api-key
BUDGET=1000000
TASKS=./task-dir
```

`.env` указан в `.gitignore`, не коммитьте его. Переменные можно задать и напрямую в окружении: они имеют приоритет над `.env`.

## Запуск

```bash
python main.py
```

Так же, как запускает жюри, с папкой задач в аргументе:

```bash
python run_agent.py --tasks-dir ./task-dir
```

`run_agent.py` принимает ещё `--out` (файл решений) и `--budget`; аргументы превращаются в переменные `TASKS`, `OUT` и `BUDGET`.

## Четыре модели регламента на OpenRouter

На прокси соревнования модели без рассуждений — отдельные (`…-noreason`). На OpenRouter их нет, поэтому с `NOREASON_VIA_REQUEST=1` имя с суффиксом `-noreason` отправляется как базовая модель с выключенными рассуждениями. Так можно планировать, запускать и измерять все четыре модели под теми же именами, что в финале:

```dotenv
NOREASON_VIA_REQUEST=1
MODELS=qwen/qwen3.8-27b,qwen/qwen3.8-27b-noreason,qwen/qwen3.6-35b-a3b,qwen/qwen3.6-35b-a3b-noreason
```

Чтобы измерить одну модель, оставьте в `MODELS` только её и задайте `TRAJECTORIES`: каждая задача допишет в файл строку с оценкой, фактическим расходом, временем и исходом.

## Запуск в Docker

```bash
docker build -t hack:latest .
```

```bash
docker run --rm -e LLM_BASE_URL -e LLM_API_KEY -v "$PWD/task-dir:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp hack:latest --tasks-dir /data/tasks
```

- **Только для чтения:** рядом с кодом ничего не пишется. `main.log` уходит в `/tmp`, `solutions.json` — в папку задач, `answer.txt` — в папку каждой задачи.
- **Бюджет:** команда жюри его не передаёт, поэтому берётся `DEFAULT_BUDGET`. Он намеренно большой: задачи идут по убыванию баллов на единицу расхода, ответы сохраняются сразу, и прогон продолжается, пока прокси не перестанет отвечать. Если бюджет известен, его лучше задать через `BUDGET` или `--budget`.
- **Зависимости:** прямые зафиксированы в `requirements.txt`, все остальные — в `constraints.txt`. Ключей в образе нет: `.env` исключён через `.dockerignore`.

Каждая подпапка в папке задач должна содержать `task.json` (поля `task_id`, `task_type`, `instruction`, `reward`) и, при необходимости, `workspace/` с файлами задачи.

## Параметры в `config.py`

- `JUDGE_MODEL_NAME`: модель, которая оценивает задачи
- `MODEL_NAME_LIST`: модели, для которых делается оценка
- `TIME_LIMIT_IN_SECONDS`: лимит времени на прогон
- `RUN_SAFETY_MARGIN_SECONDS`: запас в конце часа, который план не занимает
- `COST_BY_TASK_TYPE`, `SECONDS_BY_TASK_TYPE`, `DEFAULT_TASK_COST`, `DEFAULT_TASK_SECONDS`, `MODEL_COST_FACTOR`: таблицы оценки расхода и времени по типам задач и поправка на модель
- `PRECHECK_CONTRADICTORY_TESTS`, `PRECHECK_MISSING_INPUTS`: проверки невыполнимости без вызовов модели; каждую можно выключить
- `USE_JUDGE`, `COST_PER_STEP`, `SECONDS_PER_STEP`, `DEFAULT_STEPS`: оценка моделью-судьёй (выключена) и цена шага для неё
- `CONTEXT_MAX_CHARS`, `CONTEXT_MAX_FILES`, `CONTEXT_HEAD_LINES`: сколько содержимого файлов задачи показывать агенту в первом сообщении
- `PARALLEL_SESSIONS`: сколько задач решается одновременно (до 5 по регламенту)
- `SECOND_PASS`: тратить ли остаток бюджета на задачи без ответа и на отброшенные планом
- `FALLBACK_MODELS`, `MAX_MODELS_PER_TASK`: запасные модели по порядку и сколько моделей пробовать на одну задачу
- `SOLVER_MAX_ITERATIONS`, `SOLVER_MAX_TOKENS`: шагов агента на попытку и выходных токенов на вызов
- `MAX_TOKENS_BY_TASK_TYPE`, `TASK_COST_CAP_BY_TYPE`: лимит вывода на вызов и предел расхода на задачу для отдельных типов (у задач на код они выше)
- `TASK_COST_CAP`: предел расхода на одну задачу
- `FALLBACK_MAX_SPENT`: вторая модель пробуется, только если первая потратила не больше этого
- `CALL_RESERVE_MARGIN`: запас к резерву бюджета на один вызов модели
- `TASK_TIMEOUT_SECONDS`, `BASH_TIMEOUT_SECONDS`: таймауты попытки и одной команды
- `MAX_CONSECUTIVE_LLM_ERRORS`, `LLM_ERROR_RETRIES`: сколько ошибок подряд считать отказом прокси и сколько раз повторять попытку после ошибки

## Оценка расхода

1. **Без вызовов модели:** стоимость и время задачи берутся из таблиц `COST_BY_TASK_TYPE` и `SECONDS_BY_TASK_TYPE` по её типу (`DEFAULT_TASK_COST` и `DEFAULT_TASK_SECONDS` для неизвестного типа). Это средние по прогону на 100 задачах, по 25 каждого типа, включая нерешённые и невыполнимые: заранее их не отличить.
2. **Поправка на модель:** стоимость умножается на `MODEL_COST_FACTOR` модели. Единицы бюджета: выходные токены + входные / 10. Таблица измерена на `qwen3.6-35b-a3b`; коэффициенты моделей `-noreason` пока не измерены.
3. **План:** выбор задач и моделей учитывает остаток бюджета и остаток часа за вычетом `RUN_SAFETY_MARGIN_SECONDS`. Сессии идут параллельно, поэтому время задачи делится на `PARALLEL_SESSIONS`.
4. **Невыполнимые задачи, видимые без модели** (`precheck.py`), в план не попадают:
   - **противоречивые тесты:** один и тот же вызов с константными аргументами должен вернуть два разных результата, так что никакой код не пройдёт все тесты;
   - **нет входного файла:** файл или папка, которые условие велит прочитать, отсутствуют в папке задачи (файлы, которые условие просит создать, не считаются).

   На сгенерированном наборе из 100 задач эти проверки нашли 9 невыполнимых из 20 и не задели ни одну из 80 выполнимых. Остальные невыполнимые задачи определяет агент на первом вызове (см. «Решение задач»).
5. **Калибровка:** с переменной `TRAJECTORIES` прогон записывает по каждой задаче оценку и факт. По этим данным обновляются `COST_BY_TASK_TYPE`, `SECONDS_BY_TASK_TYPE` и `MODEL_COST_FACTOR`; после изменений агента таблицы нужно перемерить.
6. **Судья (выключен):** `USE_JUDGE=1` возвращает оценку моделью-судьёй — один вызов на задачу, ответ «выполнима ли и сколько шагов». Выключен, потому что на 100 задачах стоил 5313 единиц и распознал 4 невыполнимые задачи из 20: большинство из них видно только по файлам, которые судья не читает.

## Решение задач

После DP `main.py` решает выбранные задачи (`executor.py`, `solver.py`):

1. **Порядок:** задачи идут по убыванию отношения награды к оценке токенов, до `PARALLEL_SESSIONS` одновременно.
2. **Агент:** на каждую задачу создаётся агент openJiuwen с тремя инструментами. `bash` выполняет команду в папке задачи, а с `final=true` её вывод сразу становится ответом; `submit` сдаёт ответ; `give_up` завершает задачу как невыполнимую.
   - **Файлы в первом сообщении:** небольшая рабочая папка показывается агенту целиком (до `CONTEXT_MAX_CHARS` символов), большая — первыми строками файлов. Для задач на код добавляется вывод тестов. Агент не тратит вызовы на `ls` и `cat`.
   - **Невыполнимые задачи:** подсказка перечисляет признаки, при которых нужно сразу вызвать `give_up`: количество задано словом, а не числом; шаг не определён (деление на ноль); файла, колонки, поля или записи из вопроса нет; тесты противоречат друг другу. Имена и термины из условия, которых нет ни в одном файле, передаются агенту отдельной строкой `Note`. После `give_up` ответ не сохраняется и вторая модель не запускается. Если агент вместо этого сдаёт через `submit` текст отказа («не хватает данных», `None`, `N/A`), это тоже считается отказом и ответом не сохраняется.
3. **Проверка ответа:** для задач с `check: unittest` ответ принимается, только если тесты проходят. Изменённые агентом тесты восстанавливаются.
4. **Сохранение:** принятый ответ сразу пишется в `answer.txt` в папке задачи и в её `workspace/`, а также в файл решений: `OUT` или `solutions.json`.
   - **`answer.txt` от агента:** текст задачи просит записать ответ в `answer.txt`. Если команда агента сделала это сама, содержимое файла принимается как ответ, что бы команда ни напечатала. Файл, оставшийся от прошлого прогона, перед попыткой удаляется.
5. **Вторая попытка:** если запланированная модель не дала принятого ответа и потратила не больше `FALLBACK_MAX_SPENT`, задача пробуется со следующей моделью из `FALLBACK_MODELS`.
   - **Второй проход на остаток бюджета:** когда план выполнен, а бюджет и время остались, задачи без ответа получают ещё одну попытку — на модели, которая их ещё не пробовала, а если такой нет, на той же. В этот же проход идут задачи, которые план отбросил из-за бюджета. Задачи, от которых агент отказался как от невыполнимых, не повторяются. Баллы важнее токенов: расход учитывается только при равенстве баллов. Выключается через `SECOND_PASS` в `config.py`.
6. **Доступность моделей:** до оценки программа одним коротким вызовом проверяет, какие модели доступны ключу (бесплатный тариф может включать не все). Недоступные не оцениваются и не попадают в план. Если 403 всё же придёт во время решения, задача переходит на другую модель.
7. **Лимиты запросов (429):** если прокси отвечает «слишком много запросов», программа ждёт столько, сколько он просит («повторите через N с»), и повторяет тот же вызов. Агент при этом не теряет уже сделанные шаги. Так же ведёт себя опрос судьи. Настройки в `config.py`: `RATE_LIMIT_*`.
8. **Жёсткий предел бюджета:** перед каждым вызовом модели резервируется его худший случай: вход / 10, полный `SOLVER_MAX_TOKENS` вывода и запас `CALL_RESERVE_MARGIN`. Вызов делается, только если потраченное, резервы уже идущих вызовов и его собственный резерв помещаются в бюджет (`BUDGET` минус расход до начала решения). Если мешают только чужие резервы, вызов ждёт их завершения; если не помещается и без них, задача останавливается. Задача не начинается, когда на один полный вызов бюджета уже нет. Так прогон не выходит за бюджет даже при пяти параллельных сессиях; ценой этого в конце может остаться неиспользованным меньше одного резерва.
   - **Учёт рассуждений:** стоимость вызова — вход / 10 плюс всё сгенерированное. Сгенерированное берётся как «всего токенов минус вход», поэтому рассуждения учитываются один раз, в каком бы поле провайдер их ни вернул.
9. **Остановка:** решение также прекращается, если прокси перестал отвечать.

Расход считается по правилам соревнования: выходные токены + входные / 10.

**Windows:** команды агента выполняются в Git Bash. `C:\Windows\System32\bash.exe` — это WSL, там нет вашего Python и Windows-путей задач, поэтому он не используется. При старте программа проверяет, что `python3` работает, и останавливается с понятной ошибкой, если нет.

**Внимание:** решение меняет файлы задач (`answer.txt`, исправленный код в `workspace/`). Для пробных запусков указывайте в `TASKS` копию `task-dir`.

### Тестовый набор как в финале

`make_testset.py` генерирует набор задач того же вида, что финальный: те же 4 типа, те же формулировки и поля `task.json`, награды от 1 до 5 случайно. В репозитории уже лежит `task-dir-final/`: 100 задач, по 25 каждого типа, 20 из них невыполнимые.

```bash
python make_testset.py task-dir-final --count 100 --unsolvable 0.2 --seed 2026 --force
```

**Невыполнимые задачи** выглядят как обычные:

| Тип | Почему не решается |
|---|---|
| math | не хватает данных («ships some boxes per day») или деление на 0 складов |
| data_analysis | вопрос про колонку, которой нет (`discount`), или нет файла `sales.csv` |
| search | человека нет в базе, у него нет нужного поля или нет файла компании-работодателя |
| coding | два теста требуют разного результата для одного входа |

**Самопроверка генератора:** решаемая задача имеет правильный ответ, а каждый баг в коде ловится видимыми тестами. Исправленный код проходит и скрытые тесты, а противоречивые тесты не проходит никакой код.

**Служебные поля `task.json`.** Решение их не читает, их использует только подсчёт баллов:
- `expected`: эталонный ответ;
- `solvable: false`: у невыполнимых задач;
- `hidden_tests`: скрытые тесты для задач с кодом, как у организаторов.

Запуск на наборе (программа меняет файлы задач, поэтому работайте с копией):

```bash
cp -r task-dir-final task-dir-final-run
```

Затем в `.env` укажите `TASKS=./task-dir-final-run` и запустите `python main.py`.

### Подсчёт баллов как в финале

В конце прогона `main.py` проверяет сохранённые ответы по тем же правилам, что и финальная проверка, и пишет в лог балл по каждой задаче и итог. Отключается переменной `SCORE_RUN=0`. Проверку можно запустить и отдельно:

```bash
python evaluate.py путь/к/копии/задач
```

Правила зависят от поля `check` в `task.json`:

| `check` | Задача засчитана, если |
|---|---|
| `exact_int` | `answer.txt` как целое число равно `expected` |
| `exact_str` | `answer.txt` без пробелов по краям точно равен `expected`, регистр учитывается |
| `unittest` | проходят все `test_*.py` в `workspace/` и `hidden_tests` из `task.json`, если они есть |

- **Без ответа:** задача без `answer.txt` баллов не получает.
- **Без эталона:** задачи без `expected` (кроме `unittest`) не оцениваются и не входят в максимум.
- **Невыполнимые (`solvable: false`):** засчитываются как `skipped ok`, если ответа нет, и как `answered unsolvable`, если ответ есть. Баллов они не приносят и в максимум не входят, как в финале.
- **Чем финал может отличаться:** для задач с кодом в финале могут быть скрытые тесты, а правила сравнения строк регламентом не описаны.
- **Поле `expected`:** решение его не читает, его использует только подсчёт после того, как все ответы уже сохранены.
