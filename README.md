# openJiuwen

Выбирает, какие задачи из папки задач решать и какой моделью, чтобы набрать больше баллов в пределах бюджета токенов и времени, решает их агентом openJiuwen и сохраняет ответы.

## Требования

- Python 3.12 (версия зафиксирована в `.python-version`: 3.12.10)
- Доступ к OpenAI-совместимому API с моделями из `config.py`

## Установка

Windows (PowerShell):

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Linux / macOS:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Настройка `.env`

Скопируйте шаблон и заполните значения:

```bash
cp .env.example .env
```

| Переменная     | Обязательна | Описание                                                        |
|----------------|-------------|-----------------------------------------------------------------|
| `LLM_BASE_URL` | да          | Адрес OpenAI-совместимого API, например `https://host/v1`       |
| `LLM_API_KEY`  | да          | Ключ доступа к API                                              |
| `BUDGET`       | да          | Бюджет токенов на весь прогон (целое число)                     |
| `TASKS`        | нет         | Путь к папке с задачами, по умолчанию `./task-dir`              |
| `MODELS`       | нет         | Модели через запятую, если ключ даёт не все (по умолчанию все из `config.py`) |
| `PARALLEL_SESSIONS` | нет    | Сколько задач решать одновременно, по умолчанию 5. На бесплатном тарифе потолок 3 запроса сразу |
| `USE_JUDGE`    | нет         | `1` — планировать опросом модели-судьи, а не по таблице `estimates.json` |

Пример `.env`:

```dotenv
LLM_BASE_URL=https://your-llm-endpoint/v1
LLM_API_KEY=your-api-key
BUDGET=1000000
TASKS=./task-dir
```

`.env` указан в `.gitignore`, не коммитьте его. Переменные можно задать и напрямую в окружении: они имеют приоритет над `.env`.

### Другой провайдер моделей

Адрес, ключ и модели берутся из настроек, поэтому программу можно запустить на любом OpenAI-совместимом API. Для DeepSeek есть шаблон `.env.deepseek.example`:

1. Скопируйте его в `.env.deepseek` и впишите ключ. Файл указан в `.gitignore`.
2. Запустите с переменной `ENV_FILE`: `ENV_FILE=.env.deepseek python main.py`, в PowerShell `$env:ENV_FILE=".env.deepseek"; python main.py`.

Основной `.env` при этом не меняется: без `ENV_FILE` программа читает его, как раньше.

- **Модели:** `deepseek-chat` отвечает без рассуждений, как модели `-noreason`; `deepseek-reasoner` сначала рассуждает.
- **Оценки для плана:** для новых моделей замеров в `estimates.json` нет, поэтому оценки берутся у измеренных моделей с тем же режимом рассуждений. После прогона их можно получить командой `python calibrate.py`.
- **Судья:** режим `USE_JUDGE=1` требует ответа модели по JSON-схеме и на DeepSeek не проверялся.

## Запуск

```bash
python main.py
```

Каждая подпапка в папке задач должна содержать `task.json` (поля `task_id`, `task_type`, `instruction`, `reward`) и, при необходимости, `workspace/` с файлами задачи.

## Параметры в `config.py`

- `USE_JUDGE`, `JUDGE_MODEL_NAME`: планировать по таблице `estimates.json` (по умолчанию) или опрашивать модель-судью
- `MODEL_NAME_LIST`: модели, для которых делается оценка
- `TIME_LIMIT_IN_SECONDS`, `TIME_SAFETY_SHARE`: лимит времени на прогон и доля, которую разрешено занять плану
- `PARALLEL_SESSIONS`: сколько задач решается одновременно (до 5 по регламенту)
- `FALLBACK_MODELS`, `MAX_MODELS_PER_TASK`: запасные модели по порядку и сколько моделей пробовать на одну задачу
- `SOLVER_MAX_ITERATIONS`, `SOLVER_MAX_TOKENS`: шагов агента на попытку и выходных токенов на вызов
- `TASK_COST_CAP`: предел расхода на одну задачу
- `TASK_TIMEOUT_SECONDS`, `BASH_TIMEOUT_SECONDS`: таймауты попытки и одной команды
- `MAX_CONSECUTIVE_LLM_ERRORS`, `LLM_ERROR_RETRIES`: сколько ошибок подряд считать отказом прокси и сколько раз повторять попытку после ошибки

## Планирование

План строится без вызовов модели, по таблице `estimates.json`: для каждой пары «тип задачи × модель» в ней лежат расход (в единицах соревнования), время и доля успехов, измеренные на прошлых прогонах. Тип задачи берётся из `task.json`.

1. **Оценки:** для каждой задачи и каждой доступной модели берётся строка таблицы. Если для модели замеров нет, оценка берётся у моделей с тем же режимом рассуждений, а в логе появляется предупреждение.
2. **Выбор (`dp.py`):** для каждой задачи выбирается не больше одной модели так, чтобы ожидаемая награда (`reward × success`) была максимальной, а суммарный расход укладывался в бюджет.
3. **Время:** задачи решаются параллельно, поэтому плану доступно `TIME_LIMIT_IN_SECONDS × PARALLEL_SESSIONS × TIME_SAFETY_SHARE` секунд работы сессий, а не `TIME_LIMIT_IN_SECONDS`.

**Обновление таблицы.** Каждый прогон дописывает в `trajectories.jsonl` по строке на задачу: какие модели пробовались, расход, время, исход. После прогона на наборе с эталонными ответами:

```bash
python calibrate.py task-dir-final-run trajectories.jsonl
```

Скрипт пересчитает `estimates.json` по этим данным. Перед новым замером удалите старый `trajectories.jsonl`, иначе прогоны смешаются.

**Судья.** Прежний способ, опрос модели-судьи по каждой задаче и модели, включается через `USE_JUDGE=1` в `.env` или `USE_JUDGE=True` в `config.py`. На 100 задачах он стоил около 15 000 единиц и 12 минут, а его оценки слабо совпадали с фактическим расходом.

## Решение задач

После планирования `main.py` решает выбранные задачи (`executor.py`, `solver.py`):

1. **Порядок:** задачи идут по убыванию отношения награды к оценке токенов, до `PARALLEL_SESSIONS` одновременно.
2. **Агент:** на каждую задачу создаётся агент openJiuwen с тремя инструментами. `bash` выполняет команду в папке задачи, `submit` сдаёт ответ, `give_up` закрывает задачу без ответа.
3. **Проверка ответа:** для задач с `check: unittest` ответ принимается, только если тесты проходят; изменённые агентом тесты восстанавливаются. Для `exact_int` ответ вида `5322.0` приводится к `5322`, а нецелое число отклоняется с подсказкой модели.
4. **Сохранение:** принятый ответ сразу пишется в `answer.txt` в папке задачи и в её `workspace/`, а также в файл решений: `OUT` или `solutions.json`.
5. **Вторая попытка:** если запланированная модель не дала принятого ответа, задача пробуется со следующей моделью из `FALLBACK_MODELS`.
6. **Доступность моделей:** до планирования программа одним коротким вызовом проверяет, какие модели доступны ключу (бесплатный тариф может включать не все). Недоступные не попадают в план. Если 403 всё же придёт во время решения, задача переходит на другую модель.
7. **Лимиты запросов (429):** если прокси отвечает «слишком много запросов», программа ждёт столько, сколько он просит («повторите через N с»), и повторяет тот же вызов. Агент при этом не теряет уже сделанные шаги. Так же ведёт себя опрос судьи. Настройки в `config.py`: `RATE_LIMIT_*`.
8. **Отказ от невыполнимой задачи:** если данных для ответа нет (нет файла, колонки, человека в базе, числа в условии) или тесты противоречат друг другу, агент вызывает `give_up`. Задача остаётся без ответа, запасная модель не запускается.
9. **Остановка:** решение прекращается при исчерпании бюджета (`BUDGET` минус уже потраченное) или если прокси перестал отвечать.

Расход считается по правилам соревнования: выходные токены + входные / 10.

**Windows:** команды агента выполняются в Git Bash. `C:\Windows\System32\bash.exe` — это WSL, там нет вашего Python и Windows-путей задач, поэтому он не используется. При старте программа проверяет, что `python3` работает, и останавливается с понятной ошибкой, если нет.

**Внимание:** решение меняет файлы задач (`answer.txt`, исправленный код в `workspace/`). Для пробных запусков указывайте в `TASKS` копию `task-dir`.

### Тестовый набор как в финале

`make_testset.py` генерирует набор задач того же вида, что финальный: те же 4 типа, те же формулировки и поля `task.json`, награды от 1 до 5 случайно. В репозитории уже лежит `task-dir-final/`: 100 задач, по 25 каждого типа, 20 из них невыполнимые.

```bash
python make_testset.py task-dir-final --count 100 --unsolvable 0.2 --seed 2026 --force
```

**Невыполнимые задачи** выглядят как обычные:

| Тип | Почему не решается |
|---|---|
| math | не хватает данных («ships some boxes per day») или деление на 0 складов |
| data_analysis | вопрос про колонку, которой нет (`discount`), или нет файла `sales.csv` |
| search | человека нет в базе, у него нет нужного поля или нет файла компании-работодателя |
| coding | два теста требуют разного результата для одного входа |

**Самопроверка генератора:** решаемая задача имеет правильный ответ, а каждый баг в коде ловится видимыми тестами. Исправленный код проходит и скрытые тесты, а противоречивые тесты не проходит никакой код.

**Служебные поля `task.json`.** Решение их не читает, их использует только подсчёт баллов:
- `expected`: эталонный ответ;
- `solvable: false`: у невыполнимых задач;
- `hidden_tests`: скрытые тесты для задач с кодом, как у организаторов.

Запуск на наборе (программа меняет файлы задач, поэтому работайте с копией):

```bash
cp -r task-dir-final task-dir-final-run
```

Затем в `.env` укажите `TASKS=./task-dir-final-run` и запустите `python main.py`.

### Подсчёт баллов как в финале

В конце прогона `main.py` проверяет сохранённые ответы по тем же правилам, что и финальная проверка, и пишет в лог балл по каждой задаче и итог. Отключается переменной `SCORE_RUN=0`. Проверку можно запустить и отдельно:

```bash
python evaluate.py путь/к/копии/задач
```

Правила зависят от поля `check` в `task.json`:

| `check` | Задача засчитана, если |
|---|---|
| `exact_int` | `answer.txt` как целое число равно `expected` |
| `exact_str` | `answer.txt` без пробелов по краям точно равен `expected`, регистр учитывается |
| `unittest` | проходят все `test_*.py` в `workspace/` и `hidden_tests` из `task.json`, если они есть |

- **Без ответа:** задача без `answer.txt` баллов не получает.
- **Без эталона:** задачи без `expected` (кроме `unittest`) не оцениваются и не входят в максимум.
- **Невыполнимые (`solvable: false`):** засчитываются как `skipped ok`, если ответа нет, и как `answered unsolvable`, если ответ есть. Баллов они не приносят и в максимум не входят, как в финале.
- **Чем финал может отличаться:** для задач с кодом в финале могут быть скрытые тесты, а правила сравнения строк регламентом не описаны.
- **Поле `expected`:** решение его не читает, его использует только подсчёт после того, как все ответы уже сохранены.
