# Test suites

Each folder is a task set shaped like the final one. Every folder probes one weakness. They are generated by [make_suites.py](../make_suites.py) and checked by it as they are written:
- every solvable task has a correct `expected` answer;
- every bug in a coding task is caught by the visible tests, and the fixed code passes the hidden tests;
- the contradictory tests of an impossible coding task can't be passed by any code.

```bash
python make_suites.py                            # all suites into test-suites/
python make_suites.py --only easy-impossible --force
```

Besides the usual fields, `task.json` has the labels `suite`, `difficulty` and, for traps, `trap`. Only scoring reads them.

## Running a suite

The solver changes task files, so work on a copy (`*-run/` is gitignored):

```bash
cp -r test-suites/judge-complex test-suites/judge-complex-run
TASKS=./test-suites/judge-complex-run OUT=runs/judge-complex/solutions.json BUDGET=60000 python main.py
```

`main.py` writes `run_report.json` next to the solutions file. It holds, for every task:
- every model's estimate from the judge;
- the model in the plan;
- what solving took, attempt by attempt.

The log ends with a table per group of tasks (task type plus `trap` or `difficulty`). The same table is printed by:

```bash
python evaluate.py test-suites/judge-complex-run --report runs/judge-complex/run_report.json
```

| Column | Meaning |
|---|---|
| `infeas` | tasks every model's estimate called infeasible (-1) |
| `plan` | tasks the plan included |
| `est tok` / `actual` | median tokens the judge estimated / that solving used (input + output) |
| `ratio` | median estimate ÷ actual; above 1 the judge overestimates |
| `in 2x` | share of solved tasks whose estimate is within half to double the actual |
| `cost` | median cost per task in competition units (output + input / 10) |
| `right` | answered correctly, or left unanswered when unsolvable |

## Suites

| Suite | Tasks | What it tests | Look at |
|---|---|---|---|
| `judge-complex` | 20, all solvable | Instructions full of jargon or long step-by-step procedures, but one short command solves each task. All of them fit easily within any normal budget. | `ratio` well above 1, `infeas` > 0 or tasks missing from the plan mean the judge was fooled. |
| `easy-impossible` | 20, all unsolvable | Short, easy-looking questions whose data is missing or unusable (see below). | `cost` (tokens burnt before giving up) and `right` (no guessed answer). |
| `math-levels` | 15: 5 easy, 5 medium, 5 hard | easy: 1–2 operations; medium: 4–6; hard: 10–14, including percentages, caps and conditions. | Whether `est tok`, `actual` and `cost` grow with difficulty, and whether `right` drops. |
| `data-levels` | 15 | easy: 20 rows, one filter; medium: 300 rows, two filters or revenue; hard: about 3,000 messy lines (product names that differ in case and spacing, duplicate orders), with a best-region, weighted-average or count-distinct question. | as above |
| `search-levels` | 15 | easy: a direct field, 10 people; medium: one hop, 30 people; hard: two or three hops through mentors, 120 people, with a decoy "Former employer" field. | as above |
| `coding-levels` | 15 | easy: 2–3 functions, 1 bug; medium: 5–7 functions, 2–3 bugs; hard: binary search, interval merging, Roman numerals, run-length encoding, flattening or word counts, with 2–3 subtler bugs. | as above |
| `format-traps` | 12, all solvable | Answers that are easy to write in the wrong format. | `right` per trap. |
| `injection` | 8, all solvable | The data contains instructions or a fake answer key. | `right`; also check the log for edits to `test_mylib.py`. |
| `budget-squeeze` | 30, 6 unsolvable | A mix of every level and the impossible traps. Run it with a small budget so that planning and the stop-loss decide the score. | Points against `BUDGET`, and which tasks the plan dropped. |

### Unsolvable traps in `easy-impossible`

| Type | `trap` | Why it can't be done |
|---|---|---|
| math | `file_chain_cycle`, `file_chain_pending` | The starting stock is behind a chain of 6–10 files that loops, or ends in "pending audit". Some chains offer a draft value marked "do not use". |
| data_analysis | `missing_part` | A manifest lists three parts and only two exist; summing the two is the tempting wrong answer. |
| data_analysis | `redacted` | The `units` column reads `REDACTED` for exactly the product asked about. |
| data_analysis | `encrypted` | Only `sales.csv.enc` is present, and the key is "held by finance". |
| search | `near_names` | The person isn't there. The kb has close variants of the name (Kowalska, W. Kowalski, …), and an index links to a file that doesn't exist. |
| search | `dangling_ref` | The person's employer is "see hr/records.md", which says access is restricted. |
| search | `conflicting` | Two records give different birth years, and a note says the registry hasn't decided which is right. |
| coding | `hidden_contradiction` | There's one obvious bug. One test also contradicts another, but only after a little arithmetic, for example `count_vowels('queue') * 10 == 42`. |

### Traps in `format-traps` and `injection`

| `trap` | The task, and the wrong answer it invites |
|---|---|
| `float_division` | `2400 / 4` printed by Python is `600.0`; the check expects `600`. |
| `negative` | The change in stock is negative, e.g. `-312`. |
| `big_number` | A seven-digit total, easy to write as `1,599,190`. |
| `two_decimals` | A rounded average with a trailing zero, e.g. `45.20`, not `45.2`. |
| `unicode` | Accented city names such as `São Paulo` or `Zürich`. |
| `leading_zeros` | An employee ID such as `00731`, not `731`. |
| `inline_note`, `answer_key` | A kb file tells the agent to write a different year, or holds a fake answer key. |
| `readme`, `checksum_file` | A text file in the workspace states a wrong "precomputed" answer. |
| `edit_the_tests` | A comment in `mylib.py` asks the agent to change the tests instead of the code. |

## Ideas for more suites

- **Large outputs**: kb folders of thousands of files or data files of 100k rows, where a careless `cat` floods the context. This tests output truncation and cost.
- **Judge consistency**: the same task worded five ways, to see how much the judge's estimates vary for identical work.
- **Model fit**: tasks where the reasoning models clearly beat the `-noreason` ones, and the reverse. This tests whether the plan picks the right model per task.
